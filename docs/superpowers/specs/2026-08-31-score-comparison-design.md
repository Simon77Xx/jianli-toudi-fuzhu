# 简历定制前后评分对比设计说明

## 1. 目标与范围

用户需要在每次 JD 定制完成后判断“这次修改是否值得投递”。当前系统只输出修改后的投递准备度和岗位竞争匹配度，缺少原始简历基线，无法判断分数变化。

本次改动增加一组独立的“修改前”评分，并在前端与 `report.md` 中同时展示：

- 修改前分数；
- 修改后分数；
- 变化值（后 - 前，保留正负号）；
- 两组评分理由与质量约束提示。

不改变现有分数含义：投递准备度不是面试概率，岗位竞争匹配度低于 50 分仍标记为“低优先级/不建议投递”。

## 2. 方案与数据流

最终化流程使用两次独立的结构化模型调用：

1. 使用同一 JD、证据库、已确认事实和原始 LaTeX，调用基线评分提示，得到 `BaselineAnalysis`；
2. 编译原始主文件一次，仅用于基线投递准备度的编译/页数质量约束，不修改原始材料；
3. 使用现有最终定制提示生成 `FinalAnalysis`，创建定制项目并编译；
4. 对修改后分数应用现有模型门禁和编译/页数上限；
5. 将 `BaselineAnalysis`、修改后 `FinalAnalysis` 和两次编译结果传给前端与报告渲染器。

基线调用失败时直接终止本轮，不默认 0 分，也不生成不完整的“前后对比”。原始编译失败只影响基线投递准备度上限，不阻止继续生成定制版本；该失败会在基线理由和质检提示中明确标出。

## 3. 数据模型

新增 `BaselineAnalysis`：

- `delivery_score: int (0--100)`；
- `competitiveness_score: int (0--100)`；
- `delivery_reasons: list[str]`；
- `competitiveness_reasons: list[str]`。

`ResumePipeline.finalize()` 返回值新增 `baseline` 和 `baseline_compile`。不把基线写入 `JobContext`，避免改变会话恢复格式；结果目录的 `report.md` 是基线评分的持久化载体。

变化值统一由代码计算：`after - before`。模型不得直接提供变化值，避免算术不一致。展示时使用 `+N`、`-N` 或 `0`。

## 4. 前端与报告

结果区域先显示“修改前后评分对比”表格，再显示当前投递决策。表格列为：指标、修改前、修改后、变化值。随后分别展示修改前与修改后的评分理由，保证用户能定位提升或下降原因。

原有摘要、差异、缺口、建议、面试可辩护记录、下载按钮和低匹配度标记保持不变。前端与 Markdown 报告使用同一变化值计算辅助函数，避免两个出口显示不一致。

## 5. 质量与安全约束

- 基线和最终评分都必须通过 Pydantic 范围校验；
- 基线编译仅调用 `compile_latex`，禁止调用会写回源文件的压缩流程；
- 定制项目仍只从证据约束改写生成，原始上传材料不覆盖；
- API Key、基线提示和完整简历内容不写入报告之外的公开文件；
- 基线分数不代表真实面试概率，页面文案保留现有免责声明。

## 6. 测试计划

- `BaselineAnalysis` 合法范围与非法分数的模型测试；
- 变化值格式化测试（正数、负数、零）；
- 报告渲染包含修改前、修改后和变化值；
- 基线编译失败时仅限制基线准备度并保留后续定制流程；
- 运行现有单元测试、语法检查和本地网页冒烟测试。

## 7. 非目标

- 不根据前后分数自动决定是否投递；
- 不增加第三次模型调用或历史分数趋势图；
- 不把前后分数用于训练、公开统计或跨用户比较。
